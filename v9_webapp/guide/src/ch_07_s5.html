Planning ahead without writing words

If checking a concept costs a fraction of writing words, can the model plan several steps ahead by searching over concepts, and does that beat the best ordinary search at the same cost?

In one breath

  • A search tries many possible futures and keeps looking at the promising ones. Writing out words for every future is expensive.
  • S5 searches over concepts instead. The decoder only writes words for the one step the model commits to, and then the search starts again from the new real position.
  • The idea is compared with a search over tokens and with simply sampling many answers, under the same time and checker budget. The design's own confidence that the new idea wins is about 25%.

What a search is, in plain words

Suppose you must pick one of four doors, and you can peek behind each one but peeking costs time. A sensible plan is to peek at the most promising door, see what is there, and then decide whether to peek again at the same door or try another. Tree search, specifically Monte Carlo tree search (MCTS), does exactly that, thousands of times, and then chooses the door it peeked at most.

Each peek (a simulation) does four things: select a branch to try, expand it, evaluate how good it looks, and back that result up into the average for the branch. The branch is chosen by a score that adds two things: how well the branch has done so far (Q), and an exploration bonus that is larger for branches the model's prior likes (P) and branches tried rarely (small visit count N). This rule is called PUCT.

Show the formula
score(a) = Q(a) + c * P(a) * sqrt(N_total) / (1 + N(a))        c = 1.5
Q(a) = average result of the tries of branch a
P(a) = the selector's prior for code a (and the STOP judge for STOP)
N(a) = how many times branch a has been tried

At the very first simulation every score is zero, and ties go to the lowest-numbered action. With a tiny budget this makes the search pick code 1 by rule. The project notes it as a property of the formula, not a malfunction.

Why concepts make a search cheaper

In a token tree, every branch must be written out: four tokens through the encoder and the decoder, one after another. That is about 28 units of work per try. In a concept tree a try is just one code plus one step of the concept stack: about 5 units. The decoder never runs inside the lookahead. This is the "decoder removed from the search" part of the original proposal. The decoder still runs once to commit to each real step.

Plan, commit one step, replan

A GPS does not plan the whole trip once and then go blind. It plans a few turns ahead, you drive one stretch, and it plans again from where you really are. S5's main method works the same way and is called receding horizon, written RH(H) where H is how many steps it imagines ahead.

  1. Search from a real position.

    The root is the prompt plus every step already written and re-read.

  2. Imagine up to H steps, with no decoder.

    Each try follows a code, takes one cheap step in concept space, and asks the judges how good it looks.

  3. Commit to the most-visited code.

    Write its four tokens with the decoder and read them back in.

  4. Search again from the new real position.

    Stop when the best action is STOP, and send the answer to the checker.

RH(1) imagines just one step, and it is where S5 begins. There are two other shapes, both treated as experiments on the side. G(R) runs a single search for the whole puzzle and re-grounds, meaning writes and re-reads, every R steps. IMAG imagines the entire path and decodes only the winner at the very end.

How far ahead can we trust the imagination?

An imagined step is never perfect, and errors add up. If each imagined step is 95% right, then twenty in a row are right only about 36% of the time. So the lookahead depth has to be limited, and the limit is not guessed. Gate G2.3 from S2 measures it, and S5 may look ahead only as deep as the gate allows. That is why receding horizon re-reads the real position after every committed step.

The direct answer to the original question

Can the decoder be removed while searching over concepts? On this exam, in principle yes: one concept is exactly one hop, the rule for the next step is a lookup over roads the concept stack already attends to, and in an earlier version (V5), training on NCP made a model's own fed-back guesses about 18 times less harmful on graph data. What could stop it is a list, and each item has its own gate:

  • Codes that do not write distinct legal roads (G2.4).
  • Imagined and executed positions that lead to different decisions (G2.3).
  • Judges trained on real positions that do not transfer to imagined ones (G4).
  • Wall-clock time dominated by launch overhead instead of arithmetic. This is measured first, before any comparison.

The answer will be a table over H and R, not a yes or no.

The rivals, and the add-on loop

The new idea has to beat the best ordinary alternatives, not a weak one. Under one shared wall-clock cap and one cap on checker calls, the primary matrix has five methods:

It is reported as an add-on.

Three questions, kept apart

Mechanism

Does removing the decoder from the lookahead hurt or help?

Decoder-free RH(1) against the same search with every child written out, at equal node count (which isolates how good the imagined steps are) and at equal wall-clock (which adds the cost advantage). Run on sealed hard10 at 16×.

Practical

Does it beat the best token search?

Against the token tree and best of N, each using the strongest decoder S4 produced, under the same time cap and checker-call cap. Every result names which cap was binding.

Feedback efficiency

Is it cheaper per checker call?

The same methods at a fixed number of checker calls, with runtime reported, analysed separately.

Predictions written in advance
  • L1, about 25%: decoder-free RH(1) beats the token tree on sealed hard10 at 16×. Low because the work saving may not become a time saving at this tiny width, and every earlier comparison of latent steering against a simpler search went the other way.
  • L2, about 35%: G2.3 passes at every depth up to 4.
  • H16, about 40%: decoder-free RH(1) is at least as good as grounded RH(1). At 512 puzzles a tie is expected to read as inconclusive.

The planned runtime is between about 3 and 38 hours depending on whether the search can run many puzzles at once. It is fixed only after a speed test.
